Veloq / Connect

Link API reference

Protocol 2 to 3, 115 methods. Generated from the engine's method table.

How the link works

The Veloq app on the phone holds the athlete's library. A browser page reads and edits it over a direct, encrypted connection between the browser and the phone. No server holds the library: a relay only introduces the two, and sees neither the requests nor the replies.

Pairing

  1. The browser shows a QR code holding a room id, a one-time secret, its own certificate fingerprint and an expiry.
  2. The phone scans it and the browser connects.
  3. Each side proves it holds the secret with an HMAC over both certificates, the browser with pair.prove and the phone in its answer. A relay that swapped either certificate cannot make a proof that verifies.
  4. The browser polls pair.status, which answers waiting, confirmed or declined. The athlete confirms on the phone, and only then is the browser pinned by its certificate fingerprint.

The secret is spent on its first use, whether the proof was good or bad, and an invitation lasts at most two minutes. Until a browser is pinned, the only methods the phone answers are the pairing methods; any other is answered with the error not linked. The pairing methods are not rows of the method table below.

Requests and replies

A request is {"id": n, "method": "...", "params": {...}}. Its answer is {"id": n, "result": ...} or {"id": n, "error": "..."}. The id is a number from 1 to 232 − 1 and says which request a reply answers, because replies may come in any order.

A browser withdraws a request it no longer wants with {"method": "cancel", "params": {"id": n}}. A cancel has no reply of its own: a request still queued is never run, and the reply of one already running is dropped.

Every method below is either a read, which the phone answers from a pooled connection and which can write nothing, or a write, which the phone answers by the same function its own screen calls. A phone-only operation (credentials, sign-out, clearing the library, backup, restore, linked devices, pairing, experimental and debug switches) is not a method and is refused as unknown method. The deletes the table carries are recoverable on the phone: a section is retired and a saved workout is marked removed, and the phone lists and restores either.

Framing

From protocol 3 a reply is sent as one or more binary frames of at most 16 KiB each, header included, so it fits every browser's data channel limit. Every frame starts with a 10-byte header, all numbers big-endian:

BytesFieldMeaning
0versionThe frame layout, 1.
1flagsBit 0 (1): the reply bytes, joined, are a gzip stream of the reply text. Bit 1 (2): this is the last frame of its reply.
2–5idThe id of the request answered, or 0 for an event or for the reply to a request that did not parse.
6–9sequenceThis frame's place in the reply, from 0.

A reply text longer than 4 KiB is gzipped before it is cut. A page joins the frames of one id in sequence order up to the one flagged last, inflates the result when the gzip flag is set, and parses it as the JSON above. Before protocol 3 a reply is one text message holding that JSON.

Versions

This reference describes protocol 3, and the phone still answers protocol 2. A page and a phone each name a range in link.hello and speak the highest version both hold, so an app one release behind the page keeps working. A method added within a version is additive. A method removed or reshaped, or any change to the frame layout or its encoding, raises the version. A request that names a version the phone does not speak is answered with the error version.

Reading the method sections

Each method lists the fields of its params and of its reply, and links the records and enums they name to the entries under Records and enums. A field that is not always present is written null when it has no value. A byte or float run is Base64, one base64 string. A 64-bit integer is a JSON number, exact up to 253. The same shapes, as one JSON Schema document, are schema.json beside the connect page's source.
